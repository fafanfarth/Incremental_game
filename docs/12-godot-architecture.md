# 12. 技術設計（Godot 4 / iOS・Android → Steam）

エンジンは **Godot 4**。リリースは **iOS / Android が先、Steam を後から**。

この章の目的はただひとつ ――
**後から Steam 版を出すときに、作り直しになる箇所を今のうちに潰しておくこと。**

## 12.1 なぜ Godot 4 か

| 理由 | |
|---|---|
| 2D特化で軽い | 本作に3D表現は一切ない |
| ビルドが速い | Phase 0 で分かったとおり **バランスは回して直すしかない**。反復速度が直接効く |
| デスクトップ書き出しが標準 | Steam 版のために別エンジンを用意する必要がない |
| ライセンス | MIT。売上に対するロイヤリティが無い |

**弱点は課金・広告SDKの導入**（10章）。iOS/Android の IAP とリワード広告は
Unity より手間がかかるため、12.6 の方針で最初から分離しておく。

## 12.2 Steam 版を後から出すために、今決めること

後から直すのが高くつく順に並べる。**上の4つは着手前に決めきる。**

### ① 画面のスケーリング ―― 最重要

モバイルは横画面固定（NFR-01）。Steam は任意のウィンドウサイズとフルスクリーン。

```ini
window/stretch/mode   = "canvas_items"
window/stretch/aspect = "expand"
window/size/viewport_width  = 1280
window/size/viewport_height = 720
```

- **`expand`** にすると、画面が横長になるほど**左右に余白が増える**（切れない・歪まない）
- UI は全て **アンカー基準**（上部バー＝上端、左レール＝左端、右パネル＝右端、
  下辺ボタン＝下端）で配置する。**絶対座標で置いてはならない**
- これを守れば、21:9 のウルトラワイドでも Steam Deck（1280×800）でも
  レイアウトが破綻せず、**中央盤面が広くなるだけ**で済む

> **やってはいけないこと**: 19.5:9 の実機解像度を前提に座標を決め打ちすること。
> モバイルだけなら動くが、Steam 版で全画面を組み直すことになる。

### ② 入力を「アクション」で抽象化する

タッチイベントを直接拾わず、**InputMap のアクション**を経由する。

| アクション | モバイル | Steam（後から追加） |
|---|---|---|
| `act_primary` | 下辺ボタンのタッチ | マウス左 / A ボタン / Space |
| `act_secondary` | 右パネルのタッチ | マウス右 / X ボタン |
| `nav_hub` 〜 `nav_settings` | 左レールのタッチ | 1〜4 キー / LB・RB |
| `boost` | ブーストボタン | E キー / Y ボタン |
| `pause` | （なし） | Esc / Start |

アクション経由にしておけば、Steam 版の対応は
**`project.godot` にバインドを足すだけ**で済む。

- 連打が中心のゲームなので、**キーボードの連打とマウス連打を最初から想定**しておく
- ドラッグ操作（S2 の機械配置、S4 の合成、S5 の位相合わせ）は
  `InputEventScreenDrag` ではなく **`InputEventMouseMotion` に正規化**して扱う
  （Godot は `emulate_mouse_from_touch` で吸収できる）

### ③ プラットフォーム依存を1つの窓口に閉じ込める

実績・クラウドセーブ・課金・広告・ランキングは **すべて `Platform` 経由**にする。

```
Platform（インターフェース）
  ├── MobilePlatform  … Game Center / Google Play / IAP / リワード広告
  ├── SteamPlatform   … Steamworks（実績・クラウド・入力）。広告と IAP は無効
  └── NullPlatform    … エディタと CI。何もしないが必ず成功を返す
```

**ゲームロジックからは `Platform.unlock_achievement("...")` としか呼ばない。**
Steam 版の作業は `SteamPlatform` を1つ足すだけになる。

- Steam 側は **GodotSteam の GDExtension 版**を使う。
  エンジン本体の再ビルドが不要なので、**モバイルは素の Godot のまま**でいい
- `NullPlatform` があることで、**CI と自動テストがプラットフォームSDK無しで回る**

### ④ 決定論コアを描画から分離する

これは Steam のためではなく、ハードモードとオフライン進行のため（NFR-30）。
ただし結果的に移植も楽になる。

```
core/    … ゲームロジック。Node に依存しない純粋な GDScript。60Hz 固定
ui/      … 表示だけ。core を読むが、書き換えない
```

- シミュレーションは **`_physics_process`（60Hz固定）** で進める
- 描画は `_process`。フレームレートが変わっても**残り時間も進行も変わらない**
- `core/` は `prototype/`（Python）と **同じ JSON を読み、同じ結果を出す**。
  CI で両者を突き合わせる（12.5）

## 12.3 課金モデルの違いは、すでに設計で吸収されている

Steam 版は **買い切り・広告なし**が常識であり、モバイル版の F2P モデルは使えない。

普通ならここが最大の障害になるが、**本作は10章 M-01 を守っているため問題にならない。**

> M-01: 課金・広告が提供するのは **時間短縮と利便性のみ**。
> 無課金で到達できない数値・コンテンツを作らない。

つまり **広告と IAP を全部消しても、ゲームは完全にクリアできる**。

| 要素 | モバイル | Steam |
|---|---|---|
| リワード広告6枠 | あり | **なし**（該当ボタンを出さない） |
| 監獄手帳（広告除去＋常時×1.5） | ¥730 | **最初から適用**（買い切り価格に含む） |
| 段取りパック | ¥730 | **最初から適用** |
| 脱獄章パック | あり | **なし**（周回で稼ぐのみ） |
| スキン | 個別販売 | **全部同梱** |
| 獄中日誌（サブスク） | ¥610/月 | **機能として最初から開放** |
| ハードモード「死線」 | 全無効（09章 M-04） | **そのまま**。元々課金無関係 |

**ハードモードが最初から課金・広告・永久スキルを全無効にしている**ため、
Steam 版の目玉コンテンツとしてそのまま使える。

> **設計上の注意**: 今後 M-01 を破る商品（例: 脱獄章でしか買えない永久スキル）を
> 追加すると、**その瞬間に Steam 版が成立しなくなる。**
> 10章 10.5「何を売らないか」は、Steam 移植の前提条件でもある。

## 12.4 プロジェクト構成

```
Incremental_game/
├── data/                  ← バランスの唯一の正（JSON）
│   └── stage01〜05.json      Python も Godot もここを読む
├── prototype/             ← Phase 0 の Python シミュレータ（CI のバランス判定に使い続ける）
├── godot/                 ← Godot 4 プロジェクト
│   ├── project.godot
│   ├── data/                 ← data/ から同期（tools/sync_data.py）。直接編集しない
│   ├── core/                 ← 決定論コア。Node 非依存・60Hz
│   │   ├── balance.gd           JSON ローダ
│   │   ├── sim.gd               共通エンジン（通貨・スキル・購入・検査・賄賂）
│   │   └── stages/stage01.gd    ステージ固有の稼ぎ方
│   ├── platform/             ← Platform 抽象と実装
│   ├── ui/                   ← 画面。core を読むだけ
│   └── tests/                ← ヘッドレスで回る検証
└── tools/sync_data.py     ← data/ → godot/data/ 同期と差分検査
```

**`godot/data/` を直接編集してはならない。** バランスの正は `data/` の1箇所だけ。
CI が差分を検出して落とす。

## 12.5 CI（Phase 1 より先に用意する）

Phase 0 で見つけた不具合6件は、**すべて「実装して回したら壊れていた」類**だった。
数値を目で見て見つかったものは1つもない。だから CI が先。

| ジョブ | 内容 | 落ちる条件 |
|---|---|---|
| **balance** | `prototype/run_balance.py` | 手動が目標 ±20% を外れる／放置比が 1.5〜4.0 を外れる |
| **data-sync** | `tools/sync_data.py --check` | `godot/data/` が `data/` と違う |
| **parity** | Godot をヘッドレスで起動し、同じ JSON・同じ seed で回す | GDScript 版と Python 版のクリア時間が **1% 以上ずれる** |

**parity ジョブが本設計の要**。
これがあるかぎり、GDScript 実装と Python モデルは永久に一致し続け、
バランス調整を `data/` の編集だけで回せる状態が保たれる。

## 12.6 課金・広告SDKの扱い（Godot の弱点への対処）

Godot の iOS/Android 課金・広告はプラグイン頼りで、Unity より不安定。
**だから `Platform` の裏に完全に隠し、差し替え可能にしておく。**

| 機能 | 実装 | 備考 |
|---|---|---|
| IAP | `godot-google-play-billing` / StoreKit プラグイン | Platform 経由。失敗時も進行を止めない |
| リワード広告 | AdMob プラグイン | **ロード失敗時は報酬を与えて成功扱い**（FR-62） |
| 実績・クラウド | Game Center / Play Games Services | Steam では Steamworks に差し替え |
| レシート検証 | 自前サーバ（唯一のサーバ依存） | FR-69 |

**広告・課金の実装は Phase 5 まで着手しない。**
Phase 1〜4 は `NullPlatform`（何もしないが成功を返す）で開発し、
ゲーム側が「広告が無い環境」でも完全に動くことを常に保証する。
**これがそのまま Steam 版の動作保証になる。**

## 12.8 要件

| ID | 要件 | 優先度 |
|---|---|---|
| NFR-40 | 画面は `canvas_items` × `expand` でスケールし、UI は全てアンカー基準で配置する。絶対座標を使わない | 必須 |
| NFR-41 | 入力は InputMap のアクション経由で扱う。タッチイベントを直接参照しない | 必須 |
| NFR-42 | 実績・クラウドセーブ・課金・広告・ランキングは `Platform` インターフェース経由でのみ呼ぶ | 必須 |
| NFR-43 | `core/` は Node に依存せず、`_physics_process` 60Hz 固定で進む。`ui/` は core を読むだけ | 必須 |
| NFR-44 | `NullPlatform`（SDK無し）で全機能が動作し、ゲームを最後までクリアできる | 必須 |
