# 11. Phase 0 実測結果と、設計書への反映

11.1〜11.6 はステージ1、11.7 以降はステージ2〜5 の記録。

全5ステージの経済をシミュレータで回した結果と、そこから必要になった設計変更の記録。

- 実装: [`prototype/`](../prototype/README.md)
- 再現: `python3 prototype/run_balance.py`

## 11.1 合格判定

合格条件は2つ。

1. **手動クリアが docs/05 5.3 の目標時間 ±20% に入る**
2. **放置のみ ÷ 手動 の比が 1.5〜4.0 に入る**
   - 1.5 未満 ＝ 触る意味がない（FR-14 違反）
   - 4.0 超 ＝ 放置プレイが苦行になる

放置の**絶対時間**は合格条件にしない。設計時の見積り（60/70/100/110/140分）は
成長曲線と同じく手で書いたスケッチであり、実測を正とする（11.5 と同じ判断）。

```
バランス検証  （4 試行 / 固定60Hz / seed 1..4）

ステージ            手動 中央値             範囲      目標 |      放置 中央値      比 | 判定
-----------------------------------------------------------------------
独房棟              26.6分      24.2〜26.9     25分 |       65.9分  2.47 | 合格
労役棟              30.5分      29.6〜30.6     35分 |      101.1分  3.32 | 合格
食堂棟              40.3分      39.0〜41.4     40分 |       73.4分  1.82 | 合格
医務棟              44.5分      43.7〜45.8     45分 |      167.0分  3.75 | 合格
時計塔              50.5分      50.1〜51.2     55分 |      151.9分  3.01 | 合格
```

**全5ステージ合格。** 手動の総計は 192.4分（設計上の目標は 200分）。
到達までに、設計書の数値のうち **6箇所**を直す必要があった（11.2 / 11.7）。

## 11.2 設計書の誤りとして見つかったもの

### ① 壁の層報酬が発散していた（致命的）

docs/03 3.1 の式は次のとおりだった。

```
層 n の必要ダメージ = 10 × 1.35^n
層 n の突破報酬     = 50 × 1.60^n
```

「層を進めるほど1層あたりの旨味が増える」という意図は正しいが、
比 `1.60 / 1.35 = 1.185` は **1層ごとに +18.5% の複利**であり、30層で ×164 になる。

| 層 | 必要ダメージ | 層報酬 | 報酬 ÷ その層のタップ収入 |
|---|---|---|---|
| 0 | 10 | 50 | ×5.0 |
| 10 | 201 | 5,498 | ×27.3 |
| 20 | 4,043 | 604,463 | ×149.5 |
| 30 | 81,285 | 66,461,400 | ×817.6 |

この式のまま回すと **ステージ1が 82秒でクリアできた**。

**修正**: 層報酬を `5 × 1.37^n` に変更。比 `1.37/1.35 = 1.015` ＝ 1層ごとに +1.5%。
「進むほど旨味が増える」感触は残しつつ、30層で ×1.6 に収まる。

### ② 「1回きりの固定報酬」に全体倍率が乗っていた

docs/03 3.1 の隠し物は「1回きりの固定報酬」と書かれているが、
実装の素直な読みでは全体倍率とブーストが乗る。すると層20の1個で **45万** が入り、
そこでスキルを4つ同時に買えてしまい、成長曲線がその瞬間に折れる。

**修正**: 隠し物は倍率を一切乗せない固定額とする。倍率は `hidden_item_reward_mult`
（D2 隠し場所 / D6 壁の向こう）だけが乗る。報酬も層報酬の ×5 → ×3 に下げた。

### ③ A系統の「全獲得量 ×N」が自動収入にも乗って崩壊していた（最重要）

これが最大の問題だった。A4/A5/A6（×2 / ×3 / ×5）と C5 房のボス（×3）、
さらに消灯時間（×4）がすべて自動収入に乗ると、**子分の回収時間が 1/360 になる**。

| 子分 | 素の回収時間 | 倍率が乗った後 |
|---|---|---|
| 新入り | 75秒 | **0.8秒** |
| 古株 | 229秒 | **2.5秒** |
| 掃除夫 | 750秒 | **8.3秒** |
| 看守補佐 | 2,364秒 | **26.3秒** |

回収8秒の投資は実質的に無限増殖であり、自動収入が 136,000/秒（設計想定の16倍）に達した。

**修正**: **A系統は手動（タップ・層報酬）にのみ効く。自動収入は C系統でのみ伸びる。**

この変更には副次的な利点がある。修正前の A系統は
「手動にも自動にも効く」ため **他の3系統に対して常に優位** だった。
分離によって A＝手動を鍛える枝、C＝自動を鍛える枝という役割分担が生まれ、
04章 4.1 の系統定義が実態と一致するようになった。

> **docs/04 の全ステージに適用すべき原則**:
> 「全獲得量 ×N」と書かれた効果は、**手動由来の獲得にのみ適用する**。
> 自動収入に倍率を乗せるのは、その系統専用のノードだけに限る。

### ④ 子分に上限がなかった

docs/04 の S1-C2「仲間を増やす」は「子分の購入上限 +10」とあり、
設計には上限の概念があったが、数値が定義されていなかった。
上限なしで回すと掃除夫を22体買い、自動収入が制御不能になる。

**修正**: 各ティアに定員を設定。新入り30 / 古株20 / 掃除夫12 / 看守補佐40。
看守補佐は1体 260万で目標額（100万）より高く、**クリア後にだけ意味を持つ**
という docs/03 の記述どおりの位置づけになった。

## 11.3 コスト階梯の再調整

上の4点を直した時点で手動クリアは **17.3分**。合格条件（20〜30分）に届かない。
docs/07 7.5-3 が想定していたとおり、コスト階梯の再調整を行った。

| 段 | 旧 | 新 | 比 |
|---|---|---|---|
| T1 | 50 | **50** | ― |
| T2 | 250 | **300** | ×6.0 |
| T3 | 1,200 | **1,900** | ×6.3 |
| T4 | 6,000 | **12,000** | ×6.3 |
| T5 | 30,000 | **80,000** | ×6.7 |
| T6 | 150,000 | **520,000** | ×6.5 |
| **ツリー総額** | 750,000 | **2,457,000** | |

階梯比を ×5 から **×6.2 前後**に引き上げた。
候補を並べた実測は次のとおり（手動 10試行 / 放置 6試行）。

| 階梯 | ツリー総額 | 手動 | 放置のみ | 判定 |
|---|---|---|---|---|
| 50/250/1,200/6,000/30,000/150,000（旧） | 750,000 | 17.3分 | 52.6分 | 不合格 |
| 50/250/1,200/6,000/90,000/560,000 | 2,630,000 | 23.3分 | 60.9分 | 合格（T4→T5 が ×15 で不自然） |
| 50/300/1,800/12,000/90,000/560,000 | 2,656,600 | 24.6分 | 67.6分 | 合格 |
| **50/300/1,900/12,000/80,000/520,000** | **2,457,000** | **24.3分** | **67.6分** | **採用** |

あわせて **タップの基準値を 1 → 0.35 本** に下げた。
旧値では開始直後の収入が 6/秒 となり、docs/05 5.2 が想定する 1.7/秒 の 3.5倍だった。

## 11.4 生涯獲得額の式が間違っていた

docs/05 5.1 は次のように書いていた。

```
LIFE = GOAL + TREE = 1,000,000 + 750,000 = 1,750,000
```

**反復購入（子分）への支出が数えられていない。** 実測は次のとおり。

| 用途 | 金額 |
|---|---|
| 【賄賂】T7 | 1,000,000 |
| スキルツリー T1〜T6 | 2,457,000 |
| 子分（定員まで購入） | 約 1,400,000 |
| **生涯獲得額** | **約 4,860,000** |

子分への支出はツリーの半分以上を占める。
「反復購入の逓増コストがステージ1の正体」（docs/03 3.0）である以上、これは当然であり、
**5.1 の式に第3項を足す必要がある**。

```
LIFE = GOAL + TREE + REPEAT
```

この変更は docs/08 の脱獄章の式（生涯獲得額の平方根）にも波及する（11.6）。

## 11.5 バランス上の指摘（設計判断が必要なもの）

### 抜き打ち検査の2択が成立していない

docs/02 R-09 は「期待値はほぼ同等に設定し、『安定か、加速か』の好みの表明に留める」
としているが、実測では **「袖の下」が常に優位** だった。

| 選択 | 手動クリアの中央値 |
|---|---|
| 常に「袖の下」を選ぶ | **22.7分** |
| 常に「隠す」を選ぶ | 27.4分 |

理由は構造的なもので、調整では直らない。

- 「隠す」は **成功しても何も起きない**（損失を回避するだけ）
- 「袖の下」は所持額の5%を払って **90秒 ×2 のブースト**を得る
- インクリメンタルでは所持額（ストック）より収入（フロー）の方が価値が高いため、
  **フローを買う選択肢が常に勝つ**

**採用した修正**: 「隠す」に成功したとき **90秒 ×1.5 のブースト**を与える。
成功すれば袖の下より得（×1.5 を無料で得る）、失敗すれば所持額 −10% で何も得られない
という、本物の博打になった。docs/02 R-09 を書き換え済み。

修正後の実測（ステージ1、8試行）:

| 選択 | 手動クリアの中央値 |
|---|---|
| 常に「袖の下」 | 37.6分 |
| 常に「隠す」 | 38.8分 |

差は 3% まで縮み、「安定か、加速か」の好みの表明という当初の設計意図が成立した。

### 設計曲線（05章 5.2）は実測で置き換えるべき

| 時刻 | 設計曲線の累計 | 実測の累計 |
|---|---|---|
| 2分 | 200 | 743 |
| 6分 | 2,500 | 8,807 |
| 12分 | 20,000 | 146,246 |
| 20分 | 120,000 | 1,512,750 |
| 23.5分 | ― | **4,860,379（クリア）** |

設計曲線は手で書いたスケッチであり、実際のツリー構造から出てくる曲線とは形が違う。
**フェーズの区切り（P0〜P5）という考え方は有効だが、数値は実測に置き換える。**

## 11.7 ステージ2〜5 で見つかったもの

### ① 加工チェーンの ×12 が、単独で成長予算を食い潰していた（ステージ2・重大）

docs/03 3.2 の加工チェーンは 1段ごとに価値 ×12 で、素材(1) → 部品(12) →
中間品(144) → 完成品(1,728) → 精密品(20,736)。
**この4段だけで ×20,736 の成長倍率**になる。

ステージ1の実測では、開始から終了までの総成長は約 ×3,800 だった。
つまり加工チェーン1要素が、35分ぶんの成長予算を **5倍以上超過**している。
レーン数も処理速度も機械Lvも、相対的に意味を失う。

実測: **1.8分でクリア**（目標 35分）。

**修正**: 歩留まりを導入した。

```
加工1段で価値は ×12 になるが、k個の入力から1個しかできない
正味の倍率 = 12 / k       （k = 3 なら ×4）
```

- 4段で ×20,736 → **×256** に収まり、レーン数・速度・機械Lv が意味を持つようになった
- 生産ラインとして自然な概念であり、**「歩留まり改善」系のスキルに存在理由が生まれる**
- docs/03 3.2 に反映済み

### ② ステージ3は、疑念値を無視すると破産して永久にクリアできない

docs/04 4.4 のバランス注記が警告していたとおりの壊れ方をした。

ベット率を上限まで上げ続けると疑念値が飽和し、実効期待値が 1 を下回る
（1.25 → 0.95）。すると **振るほど所持額が減る**。
購入方針が疑念値を見ていなかったため、120分回しても到達しなかった。

**これは設計の不備ではなく、設計意図が正しく機能している証拠である。**
「アクセルとブレーキ」（docs/03 3.3）が本当に必要な構造になっている。

**対応**: シミュレータ側のプレイヤーに、疑念値を見てベット率を絞る振る舞いを実装した
（45% で 4割に絞り、75% で基準値まで落とす）。

> **実装時の必須要件**: プレイヤーが疑念値と実効期待値に気づけなければ、
> 同じように破産する。docs/03 3.3 の画面構成にある
> **「ボッソの疑念 42% / 実効 1.10」の常時表示は削ってはならない。**

### ③ 倍率スタックの減衰（全ステージ）

ステージ1と同じコスト階梯・同じ目標額で、目標時間だけが長い（35〜55分）ため、
後のステージほど **総成長倍率を小さくする** 必要がある。

`prototype/tune.py` で、倍率効果の値に指数 d を掛けて二分探索した（`v → v^d`）。

| ステージ | 減衰係数 d | 手動クリア | 備考 |
|---|---|---|---|
| 2 労役棟 | 0.35 | 30.5分 | 歩留まり導入後に再探索 |
| 3 食堂棟 | 0.256 | 40.3分 | 投擲間隔も調整（手動1.8秒/自動5.0秒） |
| 4 医務棟 | 0.657 | 44.5分 | そのまま着地 |
| 5 時計塔 | 0.253 | 50.5分 | E[M] は sync_sim.py の実測値をそのまま使用 |

**ステージ3と5は減衰の下限に張り付いた。** 成長の主因が倍率ではなく
非倍率の要素（ベット率・レーン数・デューティ比）だからで、
それぞれ投擲間隔と `taps_for_full_speed` を別途調整した。

### ④ 放置の絶対時間は合格条件から外した

docs/05 5.3 の放置時間（60/70/100/110/140分）は成長曲線と同じ手書きの見積りで、
実測とは形が合わない。**比（放置÷手動）を 1.5〜4.0 に収める**ことを条件に変更した。

| ステージ | 手動 | 放置 | 比 |
|---|---|---|---|
| 1 独房棟 | 26.6分 | 65.9分 | 2.47 |
| 2 労役棟 | 30.5分 | 101.1分 | 3.32 |
| 3 食堂棟 | 40.3分 | 73.4分 | 1.82 |
| 4 医務棟 | 44.5分 | 167.0分 | 3.75 |
| 5 時計塔 | 50.5分 | 151.9分 | 3.01 |

調整の過程で、比が **1.42（ステージ2の初期値）** になった状態があった。
これは「触っても触らなくてもほぼ同じ」＝ FR-14 違反であり、
詰まり解消の手動寄与を上げて 3.32 に戻した。
逆にステージ5は初期値が **6.96** で、放置プレイが苦行だった。
手動が最大効率に達するタップ速度を下げて 3.01 にしている。

### Phase 1 に進む前に守ること

1. **`run_balance.py` を CI に載せる。**
   合格なら終了コード 0、不合格なら 1 を返す。
   本章の不具合6件は **すべて「実装して回してみたら壊れていた」類**であり、
   数値を目で見て見つけられたものは1つもない。
2. **バランス調整は `prototype/data/*.json` の編集だけで完結させる。**
   実装側がマジックナンバーを持った瞬間、シミュレータと実機が乖離して
   検証そのものが無意味になる。
3. **固定60Hz・描画分離を最初から守る**（docs/09 NFR-30）。
