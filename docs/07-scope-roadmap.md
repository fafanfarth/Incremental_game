# 07. 開発スコープとロードマップ

## 7.1 スコープの切り方

本作の最大のリスクは **「ステージが5つある ＝ ミニゲームを5本作る」** 点にある。
実質的に小さなゲームを5本作る企画であり、全てを同時に作り始めると必ず破綻する。

そこで **1本を最後まで通してから、横に広げる**。

## 7.2 フェーズ

### Phase 0 — 数値プロトタイプ（1〜2週）　**✅ 完了**

> 実装: [`prototype/`](../prototype/README.md) ／ 結果: [11章](11-phase0-findings.md)
> 合格条件を満たした（手動 23.9分 / 放置 66.3分）。
> 到達までに設計書の数値のうち4箇所の誤りを修正し、コスト階梯を ×5 → ×6.2 に再調整した。

UI をほぼ作らず、ボタンとテキストだけで **ステージ1の経済** を実装する。

- 目的: 5章の成長曲線（P0〜P5）が実際に 25分で回るか、およびクリア後 CPS から継承ノードへの到達時間の検証
- **同時に、ゲームロジックを描画から分離し、固定60Hz で進む形で書く**（09章 NFR-30）。
  ハードモードの残り時間がフレームレートで変わってはならず、
  オフライン進行の正確さとバランス検証の再現性にも効く
- 成果物: Web で動く数値シミュレータ。スキル24ノードとコスト階梯が外部JSON
- **合格条件**: 手動プレイで 25分±5分、放置のみで 60分±15分に着地する

### Phase 1 — 垂直スライス（4〜6週）
**ステージ1のみを製品品質で完成させる。**

- 壁削りミニゲーム、子分、消灯時間、スキルツリーUI、抜き打ち検査、看守ガルドの賄賂演出
- セーブ / オフライン進行 / 設定（音の個別ON/OFF）
- **横画面レイアウトの骨格**（上部バー・左レール・中央盤面・右パネル・下辺の左右ボタン）
- **合格条件**: 社外テスター10名が「独房棟をクリアして、次が遊びたい」と言う
- **追加の合格条件**: 棟1クリア後 10分の放置で S1-L1（300万）に到達すること（04章 4.7.8）

### Phase 2 — 横展開（各 3〜4週 × 3）
ステージ2〜4 を1本ずつ追加する。Phase 1 で確立した
**共通フレーム（通貨カウンタ / ツリー / 検査 / 賄賂）は再利用** し、
新規実装はミニゲーム本体と固有ギミックのみに限定する。

- 各ステージ完成ごとに Phase 0 の数値検証を再実施
- この時点で「共通フレームに載らないミニゲーム案」は **落とす**

### Phase 3 — ステージ5とエンディング（6週）
時計塔は **完全な新規ミニゲーム**（周期同期パズル）なので、再利用がほとんど効かない。
Phase 2 の各ステージより 2週ほど長く見積もること。

- 巡回レーンの描画・位相ドラッグ・周期書き換えUI
- 平均倍率 E[M] のリアルタイム算出と常時表示
- GOLDEN WINDOW 演出、所長ヴァレンの対話、門の解錠カットシーン、エンディング
- **先に `docs/tools/sync_sim.py` で周期範囲の設定を確定させてから実装に入る**

### Phase 4 — 周回と永久スキル（4週）
- 記録抹消（プレステージ）、脱獄章の算出、**永久スキル表 30項目**（08章）
- 周回導線と、エンディング後にだけ表れるUI
- 実績 50件、図鑑、年表

### Phase 5 — 課金・広告（3週）
- リワード広告6枠、IAP（買い切り3種＋章パック3種＋スキン）、レシート検証（10章）
- **ハードモードでの全無効化**の実装と、モードごとの効果適用テーブル

### Phase 6 — ハードモード「死線」（3週）
- 死線専用セーブ、残り時間のカウントダウンと加算、難易度3段階
- 各ステージの時間ボーナス（既存のサブ目標の読み替えなので新規実装は小さい）
- **投資回収期間の算出と超過警告**（09章 9.6）。このモード唯一の新規UI
- 自己記録とプラットフォームのリーダーボード連携（参考記録）
- **サーバ実装は不要**。リプレイ検証を伴う順位表は実装しない（09章 9.7）

### Phase 7 — 仕上げ（3週）
- ローカライズ（英語）、パフォーマンス最適化（NFR-21 / 22）、ストア素材
- 死線 I〜III の時間配分の最終調整（`lethal_budget.py` の想定値を実測で置き換える）

### Phase 8 — Steam 版（3〜4週・モバイル版リリース後）
[12章 12.7](12-godot-architecture.md) のとおり。
**12.2 の①〜④を守っていればこれで済む。守らなければ倍以上かかる。**

- `SteamPlatform`（実績・クラウド・入力）、キーボード／ゲームパッド／マウス
- ウィンドウ・解像度・フルスクリーン・Steam Deck 検証
- 課金導線の除去と同梱コンテンツへの置換（10章 M-01 のおかげで再バランス不要）
- 英語ローカライズの仕上げ、ストアページ

**合計: 約 8〜9ヶ月**（少人数チーム想定）／ Steam 版はその後 3〜4週

> 競技ランキングをハードモードに差し替えたことで、
> **リプレイ検証サーバと固定小数点化が丸ごと不要になり、約2ヶ月短縮された**。
> 外部サーバに依存するのはレシート検証のみになり、運用コストも大きく下がっている。

## 7.3 MVP（最小で世に出せる範囲）

| 含む | 含まない |
|---|---|
| ステージ1〜2 | ステージ3〜5 |
| スキルツリー 2本（T1〜T7） | 周回 / 永久スキル表 |
| 固定タイムステップのシミュレーション基盤 | ハードモード「死線」 |
| リワード広告2枠（留守中の稼ぎ×2、差し入れ） | IAP 全般 |
| **継承ツリー S1-L1 / S1-L2** | L3・L4（密輸ルート） |
| **廊下（ハブ）と棟の往復** | 5棟同時進行の最適化 |
| オフライン進行・セーブ | クラウドセーブ |
| 日本語 | 英語 |
| 賄賂演出 2種 | エンディング |

MVP でも **継承ツリーの最初の2ノードと棟の往復は必ず含める**。
この仕組みが機能するかどうかが本作の成否を決めるため、
ステージを増やすより先に検証する必要がある。

MVP のエンディングは **「第3の牢屋の扉が開く」ところで To be continued** とし、
ストア上は早期アクセス／無料版として配信、以降のステージをアップデートで追加する。

## 7.4 リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ミニゲームが5本＝実質5本の開発 | 工期の爆発 | Phase 2 で共通フレームに載らない案を落とす。ステージ1〜4 で部品化を徹底する |
| ステージ5（同期パズル）が理解されない | 最終ステージで離脱 | P1 で「たまたま窓が重なって ×4」を必ず起こす。S5-B1（数値表示）を最初の50で買わせる。それでも詰まる層には S5-C6「時計係」（最良構成の自動提案）を逃げ道として用意 |
| ステージ5の周期範囲の設定ミス | 全同期が簡単に成立しステージが即終了 | A と E の設定範囲が、範囲拡張スキルを全部取っても僅かしか重ならないよう維持（04章 4.6 の注記）。`sync_sim.py` で回帰確認 |
| ステージごとに一から稼ぎ直す＝作業感 | 3ステージ目で離脱 | 継承ツリー（R-04）で「前の棟で稼ぐと今の棟が強くなる」を作る。棟2クリア直後に棟1へ戻す導線を必ず挟む（02章 2.4） |
| ステージ3のプラス期待値ギャンブル | 放置で無限増殖 | 自動投擲に試行時間とベット上限の制約（04章の注記） |
| 通貨が毎回リセットされる不快感 | 「稼いだ意味がない」 | 通貨は没収せず保持する（R-02）。賄賂はノード購入なので「使った」感覚になり、リセットされた感覚にならない |
| 継承ツリーが死に機能になる | クリア後に誰も戻らない | L ノードの効果を必ず「別の棟」に出す。廊下にバッジ通知（FR-43）。KPI「クリア後に戻った割合 60%」で監視 |
| 5棟同時進行による処理負荷 | 端末が重くなる | 非表示の棟はシミュレーションせず一括加算（NFR-21b） |
| 密輸ルートで現在の棟を遊ばなくなる | コアループの崩壊 | 流入合計を自前 CPS でキャップ（05章 5.6） |
| 手動連打の疲労 | 短期離脱 | 自動化を 25〜35% 地点に必ず配置（FR-11）。長押しオートタップを早期に開放 |
| 参考タイトルと同様の音の不評 | レビュー評価の低下 | NFR-07 / 08 を Phase 1 の合格条件に含める |
| 数値のオーバーフロー | 周回で破綻 | BigNumber を Phase 0 から導入（NFR-26） |
| 進行がフレームレートに依存する | ハードモードの制限時間が端末ごとに変わる／オフライン進行がずれる | Phase 0 からロジックを描画と分離し、固定60Hzで進める（NFR-30） |
| 横持ちで「ながらプレイ」が消える | セッション頻度の低下 | 放置とオフライン進行の価値を上げる（03章 3.0b）。7日継続率で監視 |
| 課金でハードモードが緩くなる | 難易度モードが成立しない | ハードモードで課金・広告・永久スキルを全無効化（10章 M-04）。モード別の効果適用テーブルをテストで担保 |
| ハードモードの時間配分が破綻する | 棟1で詰んで誰も再挑戦しない | 難易度ごとに加算量を個別定義し、`lethal_budget.py` でプレイヤー像別の到達点を回帰確認（09章 9.2） |
| 永久スキルがステージの緊張を消す | 周回が作業になる | 対抗ギミックは無効化しない（08章 8.4-1）。特に時計塔の周期範囲は永久スキルで広げない |
| 周回リセットが嫌われる | エンディング後に離脱 | 確認画面で失うものを全提示（08章 8.4-3）。P-C6「留守番」で緩和策を用意 |

- [x] エンジン選定 → **Godot 4**（[12章](12-godot-architecture.md)）
- [x] Godot プロジェクトの骨組み、Platform 抽象、決定論コアの移植（ステージ1）
- [ ] **CI を一度緑にする。** parity ジョブが実際に差を検出できることを確認する
- [ ] ステージ2〜5 のコアを GDScript へ移植する
- [ ] Phase 1 着手（ステージ1の垂直スライス）

CI は `.github/workflows/ci.yml` に用意済み。3つのジョブが回る。

| ジョブ | 落ちる条件 |
|---|---|
| balance | 手動が目標 ±20% を外れる／放置比が 1.5〜4.0 を外れる |
| data-sync | `godot/data/` が `data/` と違う |
| parity | GDScript 版と Python 版のクリア時間が 1% 以上ずれる |

**parity が本設計の要。** これがあるかぎり GDScript 実装と Python モデルは
一致し続け、バランス調整を `data/` の編集だけで回せる状態が保たれる。
